Why we want this analysis
--------------------------
S-LDSC (stratified LD score regression) is the field-standard method for
partitioning trait heritability across functional/cell-type annotations using
full GWAS summary statistics. CREST-GV's own enrichment method is benchmarked
against CHEERS in the paper already (a peak-overlap-based method, same family
as CREST-GV), but S-LDSC is a different, independently-motivated approach
(heritability partitioning vs. variant-overlap enrichment) and is what
reviewers at a venue like Nature Methods would expect to see as external
validation that CREST-GV's enrichment rankings agree with an established,
widely-used orthogonal method. Without it, the CHEERS comparison alone may
look like validation against a similar method rather than a genuinely
independent one.

SCOPING DECISION: one GWAS study per trait, not pooled across all studies
mapped to that trait. Standard S-LDSC practice (one flagship, well-powered
GWAS per trait); pooling summary stats across heterogeneous studies is
unusual and can introduce artifacts. Keeps item 1 (and the resulting table)
tractable -- 4 files instead of a per-trait compilation across many studies.
Selection criteria for the one study per trait (to apply once we resume):
  - full summary statistics publicly available (GWAS Catalog v2 API reports
    this directly: full_summary_stats_available + FTP link)
  - European ancestry, to match the 1000 Genomes EUR reference panel used for
    LD scores (ancestry mismatch between study and reference panel biases
    S-LDSC results)
  - largest sample size among studies meeting the above
Caveat for later: CREST-GV's own lead-variant+LD-proxy set per trait is
pooled across potentially many GWAS Catalog studies (see
local_data/genetic_variants/*.bed), so the single study picked here won't be
an exact match to that pooled definition -- acceptable simplification, worth
one sentence in Methods if this analysis makes it into the paper.

[DONE -- 2026-11-18] Item 5: per-cell-type chromatin-accessibility annotations
SCOPING DECISION: one .annot.gz per cell type (not merged per collection), to
match CREST-GV's own output granularity exactly and support a true cell-type-
level ranking comparison against S-LDSC, not just a collection-level one.
Built directly from CREST-GV's existing LanceOtron peak calls -- no new data
needed:
  /project/Wellcome_Discovery/datashare/CREST-GV_collection/<collection>/peaks/<celltype>_L-tron.bed
  (729 cell types across 15 collections: CAD, calderon, catlas_adult,
  catlas_fetal, Days7_10_13_17, FireCrest, Granulopoiesis, greenleaf_brain,
  H1_hESCs, immune_cell, ludwig2019, MPAL, pancreatic_pbmc, super_PBMC,
  Turner_byDisease)
Naively calling ldsc/make_annot.py once per (cell type, chromosome) would be
729*22 = 16,038 subprocess calls (~3s each, mostly import/parse overhead,
confirmed by timing) ~= 13h serial. Instead wrote
paper_analysis/sldsc/scripts/build_annots.py, a batched reimplementation of
the same make_annot.py logic that (a) sorts+merges each peak bed once instead
of once per chromosome, and (b) loads each chromosome's .bim once and reuses
it across all 729 cell types. Validated byte-identical output against the
original ldsc/make_annot.py on a test case (CAD/Endothelial, chr22) before
running at scale.
Ran the full build in parallel (6 workers) on the cluster: all 16,038 files
(729 cell types x 22 autosomes) built successfully in ~35 min wall-clock,
68MB total, thin-annot format (single ANNOT column, 0/1, in .bim SNP order --
matches the baselineLD_v2.2 file format already in use). Spot-checked: row
counts match each chromosome's .bim SNP count exactly; sampled files have
sensible non-trivial, non-uniform fractions of SNPs flagged (no all-zero or
all-one files).
Output: paper_analysis/sldsc/annot/<collection>/<celltype>.<chr>.annot.gz
-- gitignored (68MB, fully reproducible by rerunning build_annots.py, ~35min
on this cluster; the script itself and this doc are what's committed).
